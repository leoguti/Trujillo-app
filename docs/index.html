Conceptos básicos · 1 / 6

Docker — cajas aisladas para programas

Una "caja virtual" que contiene un programa con todo lo que necesita: sistema operativo mínimo, librerías y configs. Cada servicio del stack corre en su propia caja.

¿Por qué importa?

En vez de instalar OTP, Photon, PostgreSQL, etc. directamente en el server, cada uno corre en su propia caja Docker.

  • Si uno falla, no rompe a los demás
  • Versiones independientes — actualizas OTP sin tocar Photon
  • Reproducible: lo mismo en dev, staging y prod
  • Fácil rollback: docker compose down + redeploy

Comandos esenciales

# Ver cajas corriendo
docker ps

# Reiniciar una caja
docker restart <nombre>

# Ver lo que imprime
docker logs -f <nombre>

# Logs últimos 100
docker logs --tail 100 <nombre>

# Entrar a la caja con shell
docker exec -it <nombre> bash

docker-compose — orquestar varias cajas juntas

Un archivo docker-compose.yml describe varios containers Docker como un grupo: qué imagen, qué puertos, qué volúmenes, qué red comparten. Permite levantarlas todas con un solo comando.

Estructura de cada servicio

En el server hay un folder por servicio, cada uno con su propio compose:

/root/
├── otp/             docker-compose.yml
├── server/          docker-compose.yml
├── photon/          docker-compose.yml
├── tileserver-gl/   docker-compose.yml
├── gtfs-rt-proxy/   docker-compose.yml
└── web-landing/     docker-compose.yml

Todos comparten la red trufi-server para hablarse entre sí.

Los 3 comandos que usas 99% del tiempo

# Reiniciar (sin rebuild)
docker compose restart

# Bajar

# Ver el estado
docker compose ps

# Logs en vivo
docker compose logs -f

SSH — Secure Shell

Protocolo para ejecutar comandos en una computadora remota desde tu terminal local. Como tener una consola que está físicamente dentro del servidor — pero encriptada y autenticada por llave.

Cómo funciona la autenticación

Generas un par de llaves: una pública y una privada. La pública la subes al server (al archivo ~/.ssh/authorized_keys del usuario remoto). La privada se queda en tu máquina y nunca sale.

Cuando conectas, SSH usa criptografía para demostrar que tienes la llave privada que coincide con esa pública — sin transmitirla.

  • Sin password — más seguro y más rápido
  • La llave privada está protegida por contraseña local (passphrase)
  • Puedes agregar/quitar accesos editando authorized_keys

Setup y uso

# 1. Generar par de llaves (en tu máquina)
ssh-keygen -t ed25519 -C "tu-email@ejemplo.com"

# 2. Copiar la pública al portapapeles
cat ~/.ssh/id_ed25519.pub | pbcopy   # macOS
cat ~/.ssh/id_ed25519.pub | xclip    # Linux

# 3. (un admin ya autorizado) la agrega:
echo "ssh-ed25519 AAAA... tu-email" \
  >> /root/.ssh/authorized_keys

# 4. Conectarte
ssh root@trujillo.trufi.dev

Reverse proxy — el guardián de la entrada

Un programa que recibe TODAS las peticiones públicas (puerto 80/443) y las redirige al servicio interno correcto. En este stack lo cumple YARP (.NET 10).

Por qué importa

Solo el reverse proxy escucha públicamente. OTP, Photon, TileServer, etc. están escondidos detrás — no son accesibles directamente desde internet.

Si alguien hace GET trujillo.trufi.dev/otp/…, YARP lo manda internamente a http://otp:8080/…. Beneficios:

  • Un solo certificado SSL/TLS para todo el stack
  • Logs centralizados de todos los requests
  • No exponer servicios sensibles a internet
  • Fácil sumar/quitar backends sin tocar DNS
  • Rate limiting, auth, headers — en un solo lugar

Git submodules — incluir otros repos como subcarpetas

Un repo git puede "incluir" otros repos como subcarpetas, fijando un commit específico de cada uno. Permite versionar qué versión del código externo usas sin duplicarlo en tu propio repo.

Por qué los usamos

OTP, Photon, TileServer GL y YARP/server son repos de trufi-association (mantenidos por la comunidad Trufi). No son nuestros, pero los necesitamos en producción.

Los traemos como submódulos para:

  • Versionar exactamente qué commit corre en producción
  • Poder upgradar (o revertir) controladamente
  • No duplicar miles de líneas de código en este repo
  • Mantener attribution clara de upstream

Comandos comunes

# Clonar este repo CON submódulos
git clone --recurse-submodules <url>

# Si ya cloneaste sin submódulos
git submodule update --init --recursive

# Actualizar a últimos commits remotos
git submodule update --remote --merge

# Ver estado de cada submódulo
git submodule status

# Cambiar al main de un submódulo específico
cd server/otp
git checkout main
git pull

SSL / TLS y Let's Encrypt

El candadito verde 🔒 en el browser. Necesario para que la conexión cliente ↔ servidor sea encriptada (HTTPS) y para evitar ataques man-in-the-middle. Sin esto, la app móvil no podría hablar con OTP de manera segura.

Cómo se obtiene un certificado

Let's Encrypt es una CA (Certificate Authority) gratis y automatizada. En lugar de pagar a Comodo o DigiCert, te da certificados válidos de 90 días, renovables sin límite.

El proceso (ACME):

  • Tu server prueba que controla el dominio (HTTP-01 o DNS-01)
  • Let's Encrypt emite el certificado
  • YARP lo guarda y lo presenta en cada request HTTPS
  • 30 días antes de expirar, lo renueva automáticamente

LettuceEncrypt — la integración con YARP

LettuceEncrypt es la librería .NET que YARP usa para gestionar el ciclo de vida de certificados Let's Encrypt. Cero config manual.

// Program.cs (resumido)
builder.Services
  .AddLettuceEncrypt(opts => {
    opts.AcceptTermsOfService = true;
    opts.DomainNames = new[] {
      "trujillo.trufi.dev"
    };
    opts.EmailAddress = "admin@...";
  })
  .PersistDataToDirectory(
    new DirectoryInfo("/data/lettuce"),
    pfxPassword: null);

Los certificados persisten en /root/server/data/lettuce-encrypt/ (backupear si reinstalas).

GTFS · datos · 1 / 6

GTFS — General Transit Feed Specification

Estándar abierto de Google (2006) para describir transporte público estático: qué líneas existen, dónde están los paraderos, qué horarios siguen. Formato: un .zip con archivos .txt en CSV.

Tablas principales

  • routes.txt — qué líneas existen (Línea 19, etc.)
  • stops.txt — paraderos (lat/lon, nombre)
  • trips.txt — un viaje específico de una línea
  • stop_times.txt — horario de cada parada de cada trip
  • frequencies.txt — "cada 5 min sale un bus" (frecuencias en lugar de horarios fijos)
  • calendar.txt — qué días opera (lun-vie / fines de semana)
  • shapes.txt — geometría de las rutas (puntos lat/lon)

El GTFS de Trujillo

Vive en server/data/trujillo.gtfs.zip (18 MB). Lo consumen OTP al levantarse para construir el graph de routing.

Particularidad: usa frequencies.txt con exact_times=1. Eso significa que en lugar de listar cada bus de las 6:00, 6:05, 6:10..., el GTFS define una "plantilla" de trip y dice "se repite cada 5 min entre 5:30 y 22:00".

Esa decisión de modelado tiene una consecuencia importante en GTFS-RT — la vemos en la slide del gtfs-rt-proxy.

GTFS · datos · 2 / 6

GTFS-RT — GTFS Realtime

Extensión del estándar GTFS para datos en vivo: dónde están los buses en este momento, retrasos en tiempo real, alertas de servicio. Formato: protobuf (binario, no texto), llamado típicamente .proto.

3 tipos de mensajes

  • Vehicle positions — bus X está en lat/lon, llamando route_id, direction_id
  • Trip updates — bus X tendrá 5 min de retraso al llegar a la próxima parada
  • Service alerts — "ruta 19 cancelada hoy por desfile"

En Trujillo solo tenemos vehicle positions — los choferes reportan su ubicación cada pocos segundos.

El feed de Trujillo

El driver app (otra app, no la de pasajeros) publica el feed a S3:

https://trujillo-admin-storage.s3...
   /driver/gtfsrt/pe-trujillo.proto

OTP no consume directo ese feed. Pasa primero por el gtfs-rt-proxy, que lo enriquece (le agrega los trip_id que faltan) antes de entregárselo a OTP cada 30s.

GTFS · datos · 3 / 6

trip_id — el problema central que resuelve este sistema

Cada viaje específico de un bus tiene un trip_id único en el GTFS estático. Pero el driver app de Trujillo reporta solo route_id + direction_id + start_time — no el trip_id. OTP necesita el trip_id para predecir ETAs.

Por qué OTP lo necesita

Cuando OTP recibe una posición de bus, intenta matchear ese bus con un trip específico del GTFS. Si encuentra el trip, puede:

  • Calcular qué tan adelantado/retrasado va respecto al horario
  • Predecir cuándo llegará a las paradas siguientes
  • Ofrecer ETAs precisos a la app móvil

Sin el trip_id, OTP solo sabe "hay un bus por ahí en la línea 19" — no "el bus que sale a las 14:30 va con 5 min de retraso".

El twist de las frequencies

Como el GTFS de Trujillo usa frequencies.txt con exact_times=1, cada "trip plantilla" representa decenas de buses reales (uno cada 5 min).

El proxy resuelve esto expandiendo los trips:

# Antes (GTFS original):
trip_id = 19962292   ← plantilla cada 5 min

# Después (expandido):
19962292000000   ← bus de las 5:30
19962292000001   ← bus de las 5:35
19962292000002   ← bus de las 5:40
...
19962292000069   ← bus de las 11:15

El proxy infiere a qué slot pertenece cada vehículo cruzando route_id + direction_id + start_time con la tabla de frecuencias.

OSM — OpenStreetMap

El "Wikipedia de los mapas". Datos cartográficos libres y editables colaborativamente, con licencia ODbL. Cada calle, edificio, parque, río del mundo. La fuente única de geometría que usa todo el stack.

De dónde viene en este proyecto

El extract de Trujillo se genera con trufi-pbf-extractor, herramienta de Trufi Association que automatiza el recorte de OSM por ciudad.

Cómo funciona la herramienta

# 1. Configurar .env
CITY=trujillo
BBOX=-79.10,-8.20,-78.95,-8.05
GEOFABRIK_URL=https://download.geofabrik.de/...

# 2. Levantar el container
docker compose up

# Adentro hace:
# - download del .pbf país desde Geofabrik
# - osmium extract con el bbox configurado
# - escupe trujillo.osm.pbf en data/

El extract final vive en server/data/trujillo.osm.pbf (2.3 MB) — formato .osm.pbf (Protocol Buffer comprimido).

Quién lo consume en el stack

  • OTP — construye el grafo de calles caminables/ciclables (necesario para multi-modal: caminata + bus + caminata)
  • TileServer GL — los .mbtiles que sirve son tiles vectoriales generados desde el mismo OSM
  • Photon — indexa los nombres de calles, lugares y POIs para geocoding

Una sola fuente de verdad geográfica: cuando regeneramos el OSM con trufi-pbf-extractor, hay que regenerar los derivados (graph de OTP, mbtiles, índice de Photon) para que el sistema quede consistente.

Vector tiles + .mbtiles

Los mapas modernos no se sirven como imágenes pre-pintadas (raster), sino como pequeños fragmentos de geometría que el cliente renderiza con código. Más livianos, infinitamente zoomables, retematizables al vuelo.

Vector tiles vs raster

Raster (clásico): el server pinta una imagen 256×256 PNG y la manda al cliente. Cada zoom requiere un set distinto. Pesado y rígido.

Vector tiles: el server manda solo geometría (líneas, polígonos, puntos) en un formato binario eficiente (Mapbox Vector Tile). El cliente las dibuja con WebGL/MapLibre.

  • Texto siempre nítido (no pixela al hacer zoom)
  • Cambiar tema (oscuro / claro / satélite) sin descargar tiles nuevos
  • ~10× más liviano que raster equivalente
  • Renderizado del lado del cliente — server más liviano

El formato .mbtiles es una base SQLite con TODOS los tiles de una región indexados por (z, x, y). Trujillo entero cabe en 4.7 MB.

Pipeline en este proyecto

Generación y serving cubiertos por dos repos de Trufi Association, que arriba envuelven herramientas oficiales:

  • trufi-mbtiles-generator — wrapper Docker Compose sobre Planetiler con perfil OpenMapTiles (imagen oficial openmaptiles/planetiler-openmaptiles)
  • trufi-server-tileserver-gl — empaqueta TileServer GL como container del stack
# Flujo end-to-end:
trujillo.osm.pbf
  ↓ trufi-mbtiles-generator
  ↓   (Planetiler + OpenMapTiles)
trujillo.mbtiles  (4.7 MB)
  ↓ trufi-server-tileserver-gl
  ↓   (TileServer GL)
GET /tiles/{z}/{x}/{y}.pbf  ← MapLibre

MapLibre GL es la librería que la app móvil usa para renderizar — fork open-source de Mapbox GL (que se cerró en 2020).

GraphQL — cómo la app habla con OTP

Lenguaje de consulta para APIs (Facebook, 2015). En vez de muchos endpoints REST, hay un solo endpoint que recibe queries donde el cliente pide exactamente los campos que necesita — ni más, ni menos.

Por qué GraphQL y no REST

  • El cliente decide qué campos quiere — la app móvil ahorra ancho de banda pidiendo solo lo necesario
  • Una versión nueva de la app puede pedir más campos sin romper la API ni necesitar versionado de endpoints
  • OTP no necesita /v1/, /v2/, etc.
  • Schema fuertemente tipado y auto-documentado — IDE autocomplete
  • Una sola request puede traer datos de varias entidades relacionadas (no más N+1)

Ejemplo de query a OTP

POST /otp/routers/default/index/graphql
Content-Type: application/json

{
  "query": "{
    plan(
      from: { lat: -8.11, lon: -79.03 },
      to:   { lat: -8.10, lon: -79.05 },
      transportModes: [
        { mode: TRANSIT },
        { mode: WALK }
      ],
      numItineraries: 3
    ) {
      itineraries {
        duration
        walkDistance
        legs {
          mode
          startTime
          from { name }
          to   { name }
          route { shortName longName }
        }
      }
    }
  }"
}

El origen de los datos en vivo

La driver app — la app que usan los conductores

Toda la información en tiempo real (¿dónde está cada bus ahora mismo?) viene de una app móvil distinta: la que llevan los conductores. Es el "upstream" de nuestro pipeline. No la mantenemos nosotros — pero entender qué publica es esencial para diagnosticar el sistema.

📲 Qué hace

  • Cada conductor abre la app antes de iniciar su recorrido
  • Selecciona la línea + dirección (ej. "19" → "Centro")
  • Reporta posición GPS cada pocos segundos
  • Cierra la app al terminar el recorrido

☁️ Cómo publica

  • API que persiste en S3
  • Bucket: trujillo-admin-storage
  • Archivo: driver/gtfsrt/pe-trujillo.proto
  • Formato: GTFS-Realtime protobuf binario
  • Mensaje: vehicle positions con route_id + direction_id + start_time + lat/lon

⚠️ Lo que NO trae

  • No trae trip_id (el viaje específico)
  • No trae predicciones de tiempo
  • No trae alertas de servicio

Por eso necesitamos el gtfs-rt-proxy: para enriquecer el feed antes de que OTP lo consuma.

¿Quién la mantiene?

La driver app es de un equipo distinto (típicamente la autoridad de transporte o un contratista). Si los datos en tiempo real fallan en la app de usuario, el primer chequeo es /healthz del proxy: si entities=0, el problema está aguas arriba — en la driver app o en S3.

Cómo funciona el proxy por dentro

enrich() — qué pasa cuando llega un feed

Para cada vehículo en el feed, el proxy decide qué hacer. La mayoría de las veces, le inyecta el trip_id que falta. Cinco pasos.

1

¿Es un vehículo?

El feed puede tener entidades de varios tipos. Si no es vehículo, lo ignora.

2

¿Ya tiene trip_id?

Si sí, no hay nada que enriquecer — pasa de largo.

3

¿Tiene los datos para matchear?

Necesita route_id + direction_id + start_time. Sin alguno, no se puede.

4

Buscar en el GTFS

Llama a schedule.match() que cruza con el GTFS estático y devuelve el mejor candidato.

5

Reescribir + backfill

Inyecta el trip_id, alinea start_time, y completa el id del vehículo con la placa si faltaba.

Lo que tienes que recordar

Los stats que devuelve /healthz te dicen cómo está yendo el match: si skipped_no_schedule sube, hay desfase entre el feed del driver y el GTFS estático.

Cómo se encuentra el trip_id correcto

El GTFS declara frecuencias. El proxy busca el slot más cercano.

El GTFS estático dice "cada 5 minutos sale un bus en la línea 19". El driver app reporta una hora aproximada de salida. La función match() encuentra el slot de frecuencia más cercano y devuelve el trip_id exacto.

1

Indexar al arrancar

Lee trips.txt + frequencies.txt del GTFS y construye una tabla (route_id, direction) → lista de slots.

2

Buscar candidatos

Para cada vehículo, usa bisect (búsqueda binaria, O(log n)) sobre los slots del día.

3

Elegir el más cercano

Compara el slot anterior y el siguiente al driver-time, elige el de menor diferencia absoluta.

4

Devolver trip_id expandido

Concatena base_trip_id + índice del slot a 6 dígitos. Ejemplo: "trip_19_1" + "000037".

Requisito crítico del GTFS

El GTFS del proxy debe tener frequencies.txt. Si está expandido a stop_times.txt, el constructor lanza RuntimeError. Por eso hay dos GTFS distintos: el del proxy (1 MB, con frequencies) y el de OTP (18 MB, expandido).

Memoria al límite — free -h muestra < 200 MB libre

Diagnóstico

free -h

# Ver swap activo (si lo hay)
swapon --show

# Ver uso por container
docker stats --no-stream

# Procesos top por consumo de RAM
ps aux --sort=-%mem | head -10

Crear swap por primera vez (4 GB)

# 1. Crear el archivo (4 GB)
fallocate -l 4G /swapfile

# 2. Permisos solo root
chmod 600 /swapfile

# 3. Formatear como swap
mkswap /swapfile

# 4. Activar
swapon /swapfile

# 5. Verificar
free -h
swapon --show

Hacer el swap permanente

# Agregar a fstab para que monte al reboot
echo '/swapfile none swap sw 0 0' \
  >> /etc/fstab

# Bajar swappiness (default 60 → 10)
# para que el kernel use swap solo
# cuando RAM se agota, no antes
echo 'vm.swappiness=10' \
  >> /etc/sysctl.conf
sysctl -p

Aumentar swap existente

# 1. Desactivar el actual
swapoff /swapfile

# 2. Recrear con tamaño nuevo (8 GB)
rm /swapfile
fallocate -l 8G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile

# fstab no se toca: la entrada
# es agnóstica al tamaño

A largo plazo: subir el droplet a 8 GB de RAM, o mover Photon a otra instancia (es el que más memoria consume).

  FROM requests

Onboarding · seguridad

Cómo agregar y remover admins del sistema

Cuando entra alguien nuevo al equipo, o sale, tienes que actualizar las llaves SSH. Nunca compartas tu llave privada — cada persona usa la suya.

➕ Agregar un nuevo admin

El nuevo admin te manda su clave pública (el archivo .pub):

# En el server (tú, admin actual):
ssh root@trujillo.trufi.dev

# Editar authorized_keys
nano /root/.ssh/authorized_keys

# Pegar la línea que te mandó al final:
ssh-ed25519 AAAA... usuario@laptop

# Guardar (Ctrl+O, Enter, Ctrl+X)

# Verificar permisos correctos:
chmod 600 /root/.ssh/authorized_keys

Pedile que pruebe inmediatamente después.

➖ Remover un admin

Identifica la línea con el comentario al final (email/usuario):

# Ver llaves actuales con info
cat /root/.ssh/authorized_keys

# Cada línea termina con un comentario tipo:
# ssh-ed25519 AAAA... pepe@laptop-vieja

# Borrar la línea con el editor
nano /root/.ssh/authorized_keys
# (borrar la línea entera)

🔒 Buenas prácticas

  • Cada admin tiene su par de llaves
  • El comentario debe identificar a la persona (email)
  • Rotar llaves anualmente o ante incidente
  • Backup de authorized_keys en lugar seguro
  • Nunca commitear llaves privadas en git

📋 Auditar quién tiene acceso

# Listar todas las llaves activas
cat /root/.ssh/authorized_keys

# Contar cuántas hay
wc -l /root/.ssh/authorized_keys

# Ver últimos logins
last -F | head -20

# Logs de SSH (intentos fallidos)
journalctl -u ssh --since "1 day ago" \
  | grep "Accepted\|Failed"

🚨 Si una llave se filtró

  1. Borrar la línea de inmediato
  2. Pedirle a la persona que regenere su par
  3. Revisar logs de SSH (cualquier login sospechoso)
  4. Si hubo acceso indebido: rotar todas las llaves
💡 Tip pro: mantenete una nota en el repo o en un documento compartido con la lista de admins activos y sus emails. Cada vez que agregas o remueves alguien, actualiza esa lista.
Demo en vivo · ~10 min

Vamos a darle acceso a un nuevo admin

Generamos un par de llaves SSH desde una máquina nueva, agregamos la pública al servidor, y validamos que la persona puede entrar. Después la quitamos para no dejar accesos abiertos.

  1. Crear par de llaves: ssh-keygen -t ed25519 -C "demo@test"
  2. Copiar la pública: cat ~/.ssh/id_ed25519.pub
  3. Conectarse al server y editar /root/.ssh/authorized_keys
  4. Validar el login desde la máquina del nuevo admin
  5. Auditar: last -F para ver el acceso recién registrado
  6. Limpiar: borrar la línea agregada y verificar que ya no entra

Backup & disaster recovery

Si el droplet se pierde mañana, ¿qué necesitas para volver a tener todo funcionando? 5 cosas para backupear, 1 lista de lo que NO hace falta, plan de DR completo y dónde guardar los backups.

5 cosas a backupear

  • 1. DB de analytics (diaria)
  • 2. Certificados SSL (mensual)
  • 3. Configs de servicios (cada cambio)
  • 4. Datos GTFS / OSM / mbtiles (al actualizar)
  • 5. authorized_keys (cada cambio)

Lo que NO hace falta

  • graph.obj — se regenera
  • photon_data/ — se descarga
  • Imágenes Docker — se rebuildean
  • Logs de containers — efímeros
  • Cache del proxy — 5s

Resto de la sección

Backup · 1 / 8 · alta · diaria

1. Base de datos de analytics

PostgreSQL con la tabla requests que YARP loggea. Si se pierde, se pierde todo el histórico de tráfico — no se puede recuperar de otra fuente. Backup diario obligatorio.

Dump manual

docker exec server-db-1 \
  pg_dump -U analytics analytics \
  | gzip > backups/db-$(date +%F).sql.gz

Cron diario (3 AM)

# /etc/crontab
0 3 * * * root cd /root && \
  docker exec server-db-1 \
    pg_dump -U analytics analytics \
  | gzip \
  > /root/backups/db-$(date +\%F).sql.gz

# Rotar: borrar > 30 días
5 3 * * * root \
  find /root/backups -name 'db-*.sql.gz' \
       -mtime +30 -delete
Backup · 2 / 8 · media · mensual

2. Certificados SSL

LettuceEncrypt los re-emite automáticamente, así que técnicamente no son críticos. Pero un backup evita golpear los rate limits de Let's Encrypt si reinstalas todo y necesitas emitir muchos certs juntos.

Backup

tar czf backups/lettuce-$(date +%F).tar.gz \
  /root/server/data/lettuce-encrypt/

Restore

# Antes de levantar YARP:
tar xzf backups/lettuce-2026-04-29.tar.gz \
  -C /

# YARP los detecta automáticamente al levantar
cd /root/server
docker compose up -d

Si el backup tiene certs vigentes (no expirados), YARP los usa hasta su renovación natural — no llama a Let's Encrypt.

Backup · 4 / 8 · alta · al actualizar

4. Datos GTFS / OSM / mbtiles

Los inputs canónicos del sistema. Buena noticia: ya están en el repo (server/data/). Backupear es git push. Cada vez que se actualizan en el server, sincronizar al repo.

Sincronizar al repo

SERVER=root@trujillo.trufi.dev

# Bajar todos los inputs canónicos
scp $SERVER:/root/otp/data/trujillo.gtfs.zip \
  server/data/
scp $SERVER:/root/otp/data/trujillo.osm.pbf \
  server/data/
scp $SERVER:/root/tileserver-gl/data/trujillo.mbtiles \
  server/data/

Commit y push

git add server/data/
git commit -m "Snapshot data $(date +%F)"
git push

Total ~26 MB. Considerar Git LFS si crece mucho. Mientras estos archivos vivan en git, el repo es el backup.

Backup · 6 / 8 · qué evitar

Lo que NO hace falta backupear

Errores comunes: backupear archivos enormes que el sistema regenera solo. Ocupas espacio sin valor. Estos 5 archivos/folders son derivados — no source — y volverán a aparecer al levantar los servicios.

Archivos derivados

  • graph.obj de OTP (~20 MB) — se regenera del GTFS + OSM al primer arranque
  • photon_data/ (varios GB) — se descarga desde GraphHopper la primera vez
  • Imágenes Docker (~2 GB) — se rebuildean del compose
  • Logs de containers — efímeros, no críticos
  • Cache del proxy GTFS-RT — se reconstruye en 5s

Por qué importa

Si por error haces backup de photon_data/ diariamente:

  • Cada backup pesa varios GB
  • El backup tarda mucho más
  • El destino (S3, etc.) cobra por GB
  • El restore es más lento
  • Y al final, lo único que quieres es la lista de inputs — no el índice derivado

Regla simple: si se puede regenerar sin pérdida desde otros archivos, no lo backupees.

Backup · 7 / 8 · 🚨 disaster recovery

Server perdido — el plan de 10 pasos

Si el droplet se pierde por completo (hardware, hack, error humano), este es el playbook para volver a producción. Con todos los backups en mano, ~1 hora si tienes el flujo automatizado, ~3 horas a mano.

Pasos 1-5: nuevo server

  1. Crear nuevo droplet (Ubuntu 22.04, ≥4 GB RAM, idealmente igual al anterior)
  2. Apuntar el A record DNS al nuevo IP
  3. Instalar Docker + docker-compose
  4. git clone --recurse-submodules el repo en /root/
  5. Mover los folders del repo a /root/<svc>/ según convención

Pasos 6-10: data y arranque

  1. Subir data: scp server/data/* root@host:/root/<svc>/data/
  2. Restaurar DB: gunzip -c db-backup.sql.gz | psql ...
  3. Restaurar certs: tar xzf lettuce-encrypt.tar.gz -C /
  4. Levantar todo: docker compose up -d en cada folder
  5. Re-agregar authorized_keys de los admins

Tiempo estimado: ~1h con runbook scripteado, ~3h a mano. La graph.obj de OTP toma 2-3 min adicionales en regenerarse.

Backup · 8 / 8 · analytics DB

Backup de la DB de analytics — dump y restore en local

El backup que más vas a hacer. Dos formas de obtenerlo: bajar un dump ya generado del server, o hacer un pg_dump live en el momento. Después lo restaurás en una Postgres local para hacer queries de análisis sin tocar producción.

1️⃣ Hacer el dump y bajarlo

Una sola línea: corre pg_dump dentro del container server-db-1, lo comprime y lo descarga directo a tu máquina (sin escribir nada en el server).

SERVER=root@trujillo.trufi.dev

ssh $SERVER \
  'docker exec server-db-1 \
     pg_dump -U analytics analytics | gzip' \
  > analytics-$(date +%F).sql.gz

# Verificar
ls -lh analytics-*.sql.gz

2️⃣ Restaurar en Postgres local

# Levantar Postgres en local
# (misma imagen que producción)
docker run -d --name analytics-local \
  -e POSTGRES_USER=analytics \
  -e POSTGRES_PASSWORD=analytics \
  -e POSTGRES_DB=analytics \
  -p 5432:5432 \
  postgres:16-alpine

# Restaurar el dump
gunzip -c analytics-2026-04-29.sql.gz \
  | docker exec -i analytics-local \
    psql -U analytics -d analytics

# Conectarte para hacer queries
docker exec -it analytics-local \
  psql -U analytics -d analytics

# o desde tu cliente favorito (DBeaver,
# TablePlus, etc.) en localhost:5432
# user: analytics · pass: analytics

Trabajar sobre la copia local: rápido, sin riesgo de romper producción, y puedes probar queries pesadas sin afectar a YARP.
